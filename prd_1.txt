The product is **not**:

* a chatbot
* a life coach
* a prediction engine
* a fortune teller
* a binary yes/no decision maker
* an autonomous agent that invents facts

The LLM proposes hypotheses.

The application validates, structures, scores, stores and visualizes them.

This separation is a core architectural requirement. The intended architecture is:

```text
LLM

Hypothesis
 ↓
Validator

Simulation

Graph
```

rather than:

```text

```

This distinction is fundamental to the project.

# 12. CORE DOMAIN MODEL

The central architecture must be state-transition based.

```text
RealityState
      ↓
DecisionPoint
      ↓
Action
      ↓
StateDelta
      ↓
NewRealityState
```

The LLM proposes.

The deterministic engine applies and validates.

Example:

```json
{
  "state": {
    "location": "Salem",
    "salary": 80000,
    "relationship": "active",
    "startup_time_per_week": 10
  },
  "action": {
    "type": "relocate",
    "target": "Bengaluru"
  },
  "delta": {
    "location": ["Salem", "Bengaluru"],
    "salary": [80000, 112000],
    "family_proximity": -0.7
  }
}
```

The state engine then creates a new state.

# 14. EVIDENCE MODEL

Every important claim must have provenance.

Allowed classifications:

```text
GROUNDED
INFERRED
ASSUMED
SPECULATIVE
```

Example:

```text
"New job pays 40% more"
→ GROUNDED

"New environment may expand professional network"
→ INFERRED

"User continues startup work on weekends"
→ ASSUMED

"User eventually launches a successful company"
→ SPECULATIVE
```

This distinction is mandatory.

The UI must expose it.

# 15. PLAUSIBILITY MODEL

Never represent LLM-generated future outcomes as factual probabilities.

Do not display:

```text
72% chance of success
```

unless the system has a genuinely calibrated statistical model.

Instead use:

```text
HIGH
MEDIUM
LOW
SPECULATIVE
```

Internally the engine may use a normalized score for ranking.

Example:

```text
plausibility_score = 0.81
```

But UI:

```text
PLAUSIBILITY
HIGH

Why:
• consistent with stated constraints
• requires no major external event
• compatible with current trajectory
```

# 22. EXTRACTION RULE

The model must distinguish:

### Explicit fact

Directly stated by user.

### Inference

Reasonable interpretation of user input.

### Missing information

Required to understand the scenario but not provided.

Do not silently convert missing information into facts.

Example:

User:

> "I got an offer in Bengaluru paying 40% more."

Do not invent:

```text
rent = ₹30,000
commute = 45 minutes
company size = 500
```

Instead:

```text
UNKNOWN
```

---

# 23. MINIMAL-QUESTION POLICY

The system may ask clarification questions.

But it must ask only questions that materially change the possibility space.

Example:

```text
I can model this with what you've given me.

One thing would materially change the result:

How important is staying close to your family?

[Not important] [Somewhat] [Very important]
```

Do not ask 15 onboarding questions.

# 36. CONSTRAINT ENGINE

The LLM cannot override constraints.

Interface:

```python
class ConstraintEngine:

    def validate(
        self,
        state: RealityState,
        action: Action
    ) -> ConstraintResult:
        ...
```

Example:

```text

Monthly discretionary budget <= ₹30,000

Candidate:

Move to Bengaluru
Rent = ₹50,000

Result:

INVALID
```

Constraint violations must be explicit.

# 37. STATE TRANSITION ENGINE

This is one of the most important components.

The LLM produces:

```text
Action
```

The engine converts it into:

```text
StateDelta
```

Then:

```text
State + StateDelta
       ↓
NewState
```

The engine must preserve invariants.

Example:

```text
Past:
Current job

Fork:
Accept Bengaluru job

Future:
Bengaluru job
```

Everything before the fork remains unchanged.

---

# 38. BRANCH SCORING

Initial scoring:

```text
BranchScore =
    relevance
  + plausibility
  + novelty
  + downstream_impact
  + constraint_fit
  - redundancy
  - contradiction
```

Normalize internally.

The score is used for ranking, not presented as objective truth.

---

# 39. BEAM SEARCH

Do not generate the entire possibility tree.

Use beam search.

```text
Reality
 ├── A
 ├── B
 ├── C
 ├── D
 └── E

score

keep top K

expand

score again

keep top K
```

Initial:

```text
beam_width = 5–8
max_depth = 2
```

These values should be configuration-driven.

The purpose is controlled imagination rather than unlimited generation. 

---

# 40. SEMANTIC DEDUPLICATION

LLMs may generate:

```text
Work remotely

Negotiate remote work

Request remote arrangement
```

These may represent the same state.

Use embeddings later with pgvector.

Initial algorithm:

```text
candidate
 ↓
normalize
 ↓
compare action/state delta
 ↓
semantic similarity
 ↓
merge if sufficiently equivalent
```

Do not merge based only on text similarity.

Compare state deltas as well.

---

# 41. LAZY EXPANSION

Never generate the entire graph upfront.

Initial:

```text
REALITY
 ├── A
 ├── B
 ├── C
 ├── D
 └── E
```

When the user selects A:

```text
A
 ├── A1
 ├── A2
 ├── A3
 └── A4
```

This creates the illusion of an enormous possibility space without actually computing one.

Use:

```text
progressive generation
lazy expansion
branch pruning
semantic deduplication
state caching
```

The underlying design explicitly requires this approach.

# 55. PHASE 5 — DOMAIN ADAPTER ARCHITECTURE

Do not modify the core engine for every domain.

Define:

```python
class DomainModel(Protocol):

    async def extract_state(
        self,
        input: str
    ) -> DomainState:
        ...

    async def identify_decision_points(
        self,
        state: DomainState
    ) -> list[DecisionPoint]:
        ...

    async def generate_actions(
        self,
        state: DomainState,
        decision: DecisionPoint
    ) -> list[Action]:
        ...

    async def propagate(
        self,
        state: DomainState,
        action: Action
    ) -> StateDelta:
        ...

    async def evaluate(
        self,
        state: DomainState
    ) -> list[DimensionState]:
        ...

    async def validate(
        self,
        state: DomainState
    ) -> ValidationResult:
        ...
```

Core:

```text
WHAT IF ENGINE
       │
       ├── CareerModel
       ├── RelationshipModel
       ├── GitModel
       ├── BusinessModel
       ├── PurchaseModel
       ├── FinanceModel
       ├── HabitModel
       └── DreamModel
```

The core engine remains unchanged.

Only the domain model changes.

This adapter architecture is the intended way to keep the product domain-independent.

# 77. FINAL ARCHITECTURAL PRINCIPLE

The project should ultimately converge on:

```text
                    WHAT IF
                       │
                ┌──────┴──────┐
                │             │
           WORLD MODEL    DOMAIN MODEL
                │             │
                └──────┬──────┘
                       ↓
                 REALITY STATE
                       ↓
                DECISION POINTS
                       ↓
                    ACTIONS
                       ↓
              CONSTRAINT ENGINE
                       ↓
             CAUSAL PROPAGATION
                       ↓
                 NEW STATES
                       ↓
              BEAM SEARCH / PRUNE
                       ↓
             POSSIBILITY DAG
                       ↓
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
     EXPLORE        COMPARE       FORK AGAIN
        │              │              │
        └──────────────┼──────────────┘
                       ↓
                 USER INSIGHT
```

The long-term product is therefore not:

> "an AI app with lots of modes."

It is:

> **one counterfactual reasoning engine with multiple domain models.**

Career, relationships, Git, business, purchases, finance, habits and reflection are merely different causal worlds plugged into the same underlying engine.

That is the architectural decision that makes WHAT IF a serious AI engineering portfolio project rather than another LLM wrapper.
